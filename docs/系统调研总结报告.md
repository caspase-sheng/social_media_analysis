# 社交媒体谣言检测系统 调研总结报告

姓名：丁　　学号：（略）　　组别：软件工程综合实践第 X 组
完成时间：2026 年 3 月

## 一、选题与调研目的

这次课程项目的题目是"谣言检测界面设计"。组里讨论了两轮，一开始想过做舆情热度分析、评论情感倾向，最终定在谣言检测上，理由有两个。

一个是问题离我们近。我自己就转过一条"某超市卖过期食品"的消息，后来发现是几年前的旧闻改了个地名重发。这种事太多，平台靠人工审核忙不过来。另一个是它有明确的技术抓手：谣言检测在文本分类里算成熟问题，公开文献和数据集不少，我们能在有限时间里做出点东西。

调研要回答三个具体问题：现在识别谣言一般用什么方法，门槛在哪；有没有现成的开源工具或数据集能直接用；以我们六个大三学生的水平和三周左右的课余时间，能把哪条路线走通。

## 二、调研方式

调研分两条线。

一条是查文献。我在知网和 Google Scholar 上按"谣言检测""虚假新闻检测""rumor detection""fake news detection"检索，重点看 2011 到 2023 年之间的论文，只挑讲了具体模型和实验结果的，纯概念讨论的跳过。精读了十来篇，泛读的更多。

另一条是动手试用。我把能找到的几个谣言检测在线服务都试了一遍，包括腾讯较真、微博辟谣平台和两个英文工具，故意拿自己编的消息去测，看它们怎么反馈。

文献里 Castillo 等人 2011 年发在 WWW 上的《Information credibility on Twitter》看得比较早。它用人工抽取的特征训练分类器，比如转发数、有没有 URL、有没有问号感叹号，当时能到 80% 多的准确率。它的价值是把"可信度"这个模糊的东西拆成了能算的特征。Ma 等人 2016 年发在 IJCAI 上的那篇用 LSTM 做微博谣言检测，效果比 SVM、决策树好，但也承认黑盒特性让结论不好解释。Shu 等人 2017 年的综述《Fake News Detection on Social Media》把方法分成基于内容和基于社交上下文两类，我们做的是纯文本检测，属于前一类里最基础的一种。

## 三、谣言检测的常见做法

文献里的方法大致是三层。

**基于规则和关键词**。最原始，维护一份词汇表，出现"紧急扩散""千万别吃""内部消息"就打高分。有些平台早期风控就是这么做的。快，但造谣的人换个说法就绕过去了，误报率也高，"紧急"这种词在被证实的真消息里照样出现。

**基于人工特征加传统机器学习**。Castillo 那篇是代表。把文本特征、用户特征（注册时长、粉丝数）、传播特征（转发链形状）都抽出来，喂给逻辑回归、随机森林或 SVM。在特定数据集上效果不错，问题是特征要人工设计，换个平台数据分布变了就得重新调。

**基于深度学习**。用 CNN、LSTM 或预训练语言模型自动学表示，准确率普遍更高，代价是需要大量标注数据、要 GPU，可解释性也差。我们组没人有 GPU 环境。

关于可解释性我想多说一句。BERT 之后很多任务的榜单都被刷新了，但我试用在线工具时发现，它们往往只给一个"疑似谣言"的标签或百分比，不告诉你为什么。作为使用者，看到这种结果其实不知道该不该信。这也是我们最终没选深度模型的直接原因。

## 四、现有平台和工具的情况

腾讯较真和微博辟谣这类平台定位是辟谣信息聚合，做法是编辑人工核实后发布结论，不是自动检测。用户是去查"这条是不是已经辟过谣了"，覆盖面取决于编辑跟进了多少条。

试的两个英文工具，一个网页版一个浏览器插件，有两个共同点：输入框能接受的文本长度有限，太长的直接截断；只输出判定结果，没有中间信息。其中一个还判错了，我把一条真实的社区活动通知输进去，它判成"疑似虚假"，我猜是因为里面有"社区""通知"这类在训练集里常跟谣言共现的词。

数据集方面，英文有 LIAR、FakeNewsNet，中文有微博的不实信息数据集，但要么要申请，要么规模太大我们跑不动。学校机房配置一般，装个深度学习环境都不太顺畅。这一点直接影响了路线选择。

## 五、我们确定的技术路线

综合调研结果，我们定了 TF-IDF + 逻辑回归。理由有三条。

一是可解释。逻辑回归对每个特征都有系数，一条消息被判成谣言以后，把它的 TF-IDF 值和系数按位相乘，就能算出每个词贡献了多少，挑出正贡献最大的几个显示在界面上。这个功能我在试用商业工具时没见到，对学生作业来说是个能讲出东西的亮点。

二是对数据量要求低。我们手上只有自己编的 50 条模拟数据加上爬下来的一部分，这个规模喂给 BERT 是开玩笑的，训练逻辑回归够用。周志华老师在《机器学习》里讲得清楚，线性模型在小样本上表现通常不会太差。

三是整条链路跑得动。从 jieba 分词到 TfidfVectorizer 再到 LogisticRegression 全是 scikit-learn 现成的，pip 装上就能用，不需要 GPU。

分工上六个人分了六条线，有人管数据库，有人管爬虫，有人管预处理和模型，我负责后端接口，前端交给了另外两个同学。

## 六、开发过程里踩到的坑

这部分具体写，因为踩坑的过程比结论有用。

**conda 找不到**。我本机 conda 装在 `D:\conda`，安装时没勾选加到 PATH，在普通命令行敲 `conda` 会报"不是内部或外部命令"。查了一会儿才反应过来是找不到而不是没装。解决办法是用完整路径：`call D:\conda\Scripts\activate.bat rumor_detection`。加 PATH 也行，但我不想动系统环境变量。

**批处理文件的编码**。为了一键启动，我写了 `run.bat`，里面用中文写了提示。双击运行的时候前面几行是乱码，后面几条命令干脆没执行。查了半天才明白：cmd 读 .bat 用的是系统 OEM 编码，中文 Windows 下是 936（GBK），我保存成 UTF-8，中文那几个字节被按 GBK 解释成了乱码，字节错位以后连后面的命令都被吞了。后来把 run.bat 里的中文全删了，改成英文提示，只留 ASCII。这个坑隐蔽，因为脚本在编辑器里看着完全正常。

**jieba 装坏了**。跑预处理脚本时报 `ModuleNotFoundError: No module named 'jieba'`，但 `pip list` 里明明有。进 site-packages 一看，只剩一个 `jieba-0.42.1.dist-info` 文件夹，真正的代码目录没了，估计是之前某次安装中断留的残留，pip 看到 dist-info 就认为装好了。修法是强制重装：`pip install --force-reinstall --no-deps jieba`。这事让我养成了习惯，报"模块不存在"但 pip 显示已安装的时候，先去 site-packages 看文件到底在不在。

**中文文本进 TfidfVectorizer 全是零**。这个最费时间。我一开始图省事，把原始中文丢给 TfidfVectorizer，跑出来矩阵一行全是零。翻文档才找到原因：它默认的 `token_pattern` 是 `(?u)\b\w\w+\b`，只认两个及以上字母数字组成的串。一段中文在它眼里是一整块，切不开。所以中文得先自己分好词再拿空格拼回去送给它。这也解释了为什么要单独写 `cut_to_string` 函数。原因知道了就好办，但不知道的时候，光看"矩阵全是零"这个现象很难猜。

**数据库连接被掐断**。项目第二天接口开始偶尔报连接错误。MySQL 有 `wait_timeout`，空闲超时的连接会被服务端关掉，而 SQLAlchemy 连接池里还留着这些失效连接，下次取出来用就报错。处理办法是建引擎时加 `pool_pre_ping=True`，取连接前先 ping，不通就换；再加 `pool_recycle=3600` 定期回收。

**Session 没释放**。上面那个问题解决后才暴露出来。`database.py` 里用 `scoped_session`，同一线程复用同一个 Session，Flask 每个请求一个线程，请求处理完不去 remove，Session 就挂在那个线程上，连接也不还回去，跑久了 MySQL 直接报连接数超限。修法是在 app.py 注册 `@app.teardown_appcontext`，请求结束调一次 `close_session()`。用 scoped_session 就必须配套写 teardown，这两件事是一体的。

**不知道问题出在哪**。前后端联调时页面上什么都没有，控制台也不报错，最难查，分不清是接口没返回、格式不对还是 JS 渲染错了。后来在启动流程里加了自检，把数据库通不通、模型文件在不在直接打印出来，接口也统一了 `{code, msg, data}` 的返回结构，出错时 msg 写清原因。加上这两样，同样的问题看一眼控制台就知道卡在哪一环。

**示例数据里的假例子**。界面做完自测搜索，按提示词输了"疫苗"，一条都没有。翻 sample_data.csv 发现这 50 条里根本没出现过"疫苗"，提示词是我随手写的。功能没受影响，但演示时第一个搜的词就是空结果很难看。后来改成数据里确实存在的"小区"，能搜出 5 条。顺便记一个发现：模型输出的概率基本集中在 0.5 到 0.7 之间，很少超过 0.8，按"概率下限 0.8"筛是一条都筛不出来的，演示时设 0.5 或 0.6 比较合适。

## 七、功能验证

数据这块，爬虫联网时走真实抓取，断网或解析不到走本地 CSV，两条路都测过。50 条数据入库、去重、分词的流程跑通，重复执行不会插重复数据。

模型这块，5 折交叉验证平均 F1 约 0.92，测试集准确率约 0.87。这两个数字必须加说明：训练样本和演示数据是同一批，模型测试时看到的句子训练时基本都见过，指标偏高，不能当真实泛化能力。要验证真实效果得另找没参与训练的数据，我们没条件做。

界面这块我在浏览器里逐项点过：统计卡片数字正确；列表分页正常；搜索"小区"能命中 5 条，重置能恢复；"已处理文本"标签页表头会切换；词云正常渲染；详情页的概率条和命中关键词显示正确；点"服务器检测"会弹绿色提示条并刷新结果。人工校验接口我用测试客户端单独验过，正常提交能入库，性质参数传非法值会返回提示，不存在的 id 返回 404。

LSTM 那一版只写了训练脚本，没实际跑通，因为装 PyTorch 包太大、下载太慢。这部分在文档里标成了"后续可扩展"，不算已完成的功能。

## 八、反思与结论

技术选型要跟着约束走，不是跟着排行榜走。BERT 效果肯定比逻辑回归好，但我们没有数据、没有 GPU、也没时间调，强行上马的结果大概率是跑不起来。

可解释性比我想的重要。试用商业工具时最别扭的就是它只给结论。用户看到"疑似谣言"三个字，既不知道怎么反驳，也不知道该不该信。我们加"命中关键词"一开始只是觉得线性模型顺手能做，做出来发现它确实让界面可信了一些。

数据来源是我最不满意的地方。50 条自己编的数据，自己标标签，再拿去训练和测试，这套流程跑通说明不了任何真实效果。如果还有时间，我想从公开的中文谣言数据集里抽一部分，先不看标签训练，再拿我们的模型去测，看看真实场景下能到什么水平。
