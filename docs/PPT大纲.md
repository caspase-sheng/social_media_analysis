## 第 2 页　选题背景

**页面内容**

- 问题：社交平台消息传播快，转发门槛低，很多人先转发后核实
- 例子：一条"某超市卖过期食品"的消息，其实是几年前的旧闻改了个地名重发
- 痛点：平台靠人工审核跟不上；现有工具只给结论，不告诉人为什么
- 我们的切入点：做一条"采集—处理—判断—复核"的完整链路，并且给它配一个能操作的界面

**讲解提示**

第二页用那个例子开场，比讲道理有效。这里点一下"现有工具只给结论"这句话，因为它和后面第 7 页的可解释性呼应上了。

## 第 3 页　调研结论

**页面内容**

- 三类做法对比表：

| 做法 | 优点 | 局限 |
| --- | --- | --- |
| 规则 + 关键词 | 快 | 换个说法就绕过，误报高 |
| 人工特征 + 传统机器学习 | 效果稳定 | 特征要人工设计，换平台要重调 |
| 深度学习 | 准确率高 | 要大量标注数据、要 GPU、不可解释 |

- 试用了腾讯较真、微博辟谣和两个英文工具，都是给结论不给理由
- 公开数据集（LIAR、FakeNewsNet、微博不实信息）要么要申请，要么规模我们跑不动

**讲解提示**

不用把三类做法都讲一遍，重点说清楚"为什么我们没有选 BERT"：没有数据、没有 GPU、也没时间调参，选了跑不通反而更麻烦。

## 第 4 页　系统功能总览

**页面内容**

- 四个模块：
  1. 数据展示：统计卡片 + 消息列表分页，概率用进度条呈现（≥0.5 红、<0.5 绿）
  2. 检测结果呈现：详情页显示概率 + 命中关键词
  3. 人工校验：判为谣言 / 判为非谣言，结果落入已处理表
  4. 关键字搜索：关键词 + 概率区间 + 性质三个条件组合
- 附加：关键词词云

**讲解提示**

这一页是全局地图，讲的时候强调"每个模块都能点、都有真实数据"，因为题目本身就是界面设计，老师会重点看这个。

## 第 5 页　技术选型

**页面内容**

- 后端：Flask（文件少、逻辑直观，组里只有两人写过 Django）
- 数据库：MySQL + SQLAlchemy ORM（表结构用 Python 类写，字段注释在代码里）
- 文本处理：jieba 分词 + TfidfVectorizer
- 模型：LogisticRegression（可解释）
- 前端：原生 HTML/CSS/JS + ECharts，没引框架
- 爬虫：requests + BeautifulSoup，抓不到自动读本地 CSV

**讲解提示**

"为什么用原生前端"这个问题可以主动答：项目就两个页面，引框架反而要多花时间配置，原生写出来代码量也不大。

## 第 6 页　系统架构与数据库

**页面内容**

- 分层结构图（文字版）：
  浏览器 → Flask 路由 / API → 业务函数 → SQLAlchemy ORM → MySQL
- 三张表：
  - `raw_messages`：原始消息，含 rumor_prob、status、nature
  - `processed_messages`：人工校验后的记录，raw_id 唯一约束
  - `keywords`：词 + 词频，词云数据源
- 状态流转：未处理 → 已检测 → 已处理

**讲解提示**

讲到 status 三个状态的时候，顺手说一句"已处理的消息不能再被模型覆盖，所以检测按钮会禁用"，这是个体现设计考虑的小细节。

---

## 第 7 页　核心：模型与可解释性

**页面内容**

- 流程：清洗 → jieba 分词 → 去停用词 → TF-IDF → 逻辑回归 → 概率
- 特征：`max_features=5000`，`ngram_range=(1,2)`
- 训练样本三个来源：CSV 标注数据、人工校验记录、爬虫抓的新闻（按非谣言）
- 指标：5 折交叉验证平均 F1 约 0.54，测试集准确率约 0.96，谣言召回率约 0.5
- **如实说明**：非谣言样本远多于谣言，模型偏向判非谣言，准确率高主要来自把新闻都判对；训练样本与演示数据同源，指标不能代表真实泛化能力
- 调参时踩过的坑：只喂模拟数据时词表覆盖不到真实新闻用词，一批消息的概率会挤在同一个常数上（49.6%），加新闻样本才解决
- 亮点：把 TF-IDF 值和模型系数按位相乘，取正贡献最大的词，界面上显示"因为哪几个词被判成谣言"

**讲解提示**

这一页是全场最容易被追问的地方。指标虚高要主动说，别等老师问。可解释性那段可以现场举一个例子，比如某条消息命中"转发、紧急、千万别"。

## 第 9 页　测试结果与不足

**页面内容**

- 测试结果：接口 9 个全部通过；浏览器逐项验证列表分页、搜索、排序切换、标签页切换、词云渲染、点词筛选、一键检测、检测与校验
- 不足：
  - 训练数据自产自销，指标虚高
  - 新闻按非谣言参与训练是假设不是标注，非谣言样本过多导致谣言召回率偏低
  - LSTM 只写了代码没跑通（没装 PyTorch），属后续可扩展
  - 爬虫依赖目标网站页面结构，会失效，靠 CSV 兜底
  - 没有登录和权限控制
  - 词云只做全量词频，没有按时间或来源细分

**讲解提示**

主动讲不足比被问出来好。每条不足后面跟上"如果要继续做会怎么做"，这样听起来是在思考，不是认输。

## 附：可能被问到的问题

| 问题 | 回答方向 |
| --- | --- |
| 为什么不用 BERT？ | 没有标注数据、没有 GPU，LSTM 都没跑通，上 BERT 大概率跑不起来 |
| 0.96 的准确率可信吗？ | 不可信，训练集和测试集同源，且非谣言样本占绝大多数；谣言召回率只有 0.5 才是真实水平，我如实写在文档里了 |
| 阈值 0.5 怎么定的？ | 用的是默认值，界面上可以传别的值；现在新闻大多落在 0.1~0.3，偏可疑的才到 0.7 以上 |
| 为什么有那么多消息概率一样？ | 那是词表没覆盖到的表现，加新闻样本重训后已经没有了，记在常见报错文档第 19 条 |
| 爬虫现在还能用吗？ | 真实抓取依赖对方页面结构，不保证；断网会走本地 CSV 兜底 |
| 怎么防止重复校验？ | processed_messages 的 raw_id 加了唯一约束，先查后写 |
