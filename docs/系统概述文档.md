# 社交媒体谣言检测系统 概述文档

课程：软件工程综合实践　　项目题目：谣言检测界面设计
小组人数：6 人　　完成时间：2026 年 3 月

## 一、项目背景与目标

社交平台上的消息传播速度很快，一条没核实过的内容几个小时就能转遍整个朋友圈。转发的门槛又低，很多人看到"某地要地震""某超市卖过期食品"这类话，第一反应是提醒家里人，而不是先想想有没有依据。等到官方辟谣，影响已经出去了。平台方的人手有限，靠人工一条条看也不现实，所以想做一个能自动给出参考判断的小系统。

我们这次的目标定得比较务实：不是要做一个能上线的产品，而是把"采集数据—文本处理—模型判断—人工复核"这条链路完整跑通，并且配一个能演示、能操作的网页界面。界面是这门课的重点，题目写的就是"谣言检测界面设计"，所以前端要做到四个模块都能点、每个按钮都真的有反应，不能只放几张假图。

验收标准有三条：数据能从外面进到库里；模型能给出 0~1 的谣言概率并且能说出理由；人能对结果做二次判断，判断结果还能存下来。

## 二、系统功能概述

系统一共四个模块。

**数据展示模块**。首页顶部是四个统计卡片，显示消息总数、待人工校验数、已处理数、已确认谣言数。下面是一张消息列表，按发布时间倒序分页，每页 10 条，每条显示正文前 60 个字、来源平台、发布时间、模型算出的谣言概率和当前处理状态。概率那一列做成进度条，超过 0.5 显示红色，低于 0.5 显示绿色，扫一眼就知道哪些消息需要重点看。

**检测结果呈现模块**。除了列表里的概率条，点进详情页能看到更完整的信息：消息全文、来源、发布时间、配图、模型判定的概率，以及"这条消息因为哪几个词被判成谣言"。这一项比较有用。逻辑回归这类线性模型对每个词都有权重，把一条消息的词权重和 TF-IDF 值乘起来排序，就能挑出对判断影响最大的几个词。比如界面会告诉你这条消息主要是"转发""紧急""千万别"这几个词起了作用。老师问"模型为什么这么判"，这就是答案。

**人工校验模块**。模型给的概率只是个参考，最终定性还是得靠人。详情页底部有三个按钮：“服务器检测”重新跑一次模型，“判为谣言”和“判为非谣言”是人工结论。点完校验按钮，这条消息在 raw_messages 里的状态变成“已处理”，同时往 processed_messages 插一条记录，列表里就不再出现它。人工判断过的消息不该再被模型覆盖，所以已处理的消息“服务器检测”按钮会禁用；但人工结论本身允许改判，两个校验按钮始终可点，按钮文字会跟着当前结论变成“改为谣言”“仍判为非谣言”这种，点错了能改回来。

**批量检测**。列表页标签行右边有个“一键检测”按钮，把所有还没人工校验的消息用当前模型重跑一遍。模型重新训练过以后，库里旧的概率是用老模型算的，得刷一遍才准。点之前有一次确认，跑的过程中按钮变成“检测中...”并禁用；跑完弹窗告诉成功多少条、用了多久。已经人工校验过的消息不在处理范围内。

**关键字搜索模块**。支持三个条件组合：关键词（命中正文或命中的关键词字段都算）、谣言概率区间、人工性质。搜索结果按概率从高到低排，方便先看最可疑的。

首页最下面还有一个关键词词云，数据来自 keywords 表，能直观看出这批消息里高频出现的词是什么。词云里的词可以直接点，点一下就把消息列表按这个词筛一遍，省得再手打关键词。ECharts 没加载出来时换成文字云兜底，点词筛选同样能用。

## 三、开发环境与技术选型

开发和运行环境是 Windows + Python 3.10 + MySQL 8.4，Python 装在 conda 环境 `rumor_detection` 里，服务跑在 5000 端口。

后端用 Flask。选它的原因很直接：组里只有两个人写过 Django，而 Flask 一个文件就能起来，路由和接口逻辑都摆在明面上，谁接手都看得懂。项目就这几个接口，用不着 Django 那一整套 admin 和中间件。

数据库用 MySQL，通过 SQLAlchemy 的 ORM 操作。ORM 的好处是表结构用 Python 类写，字段注释就在代码里，改表不用去翻 SQL 文件。补充一句，`requirements.txt` 里装了 `flask-sqlalchemy` 但没用上，它本质还是 SQLAlchemy 的集成层，直接用原生 ORM 少一层封装，出问题排查时调用栈也短一些。这个包属于没清干净的遗留。

中文分词用 jieba，特征提取用 scikit-learn 的 TfidfVectorizer，分类器用 LogisticRegression，爬虫用 requests + BeautifulSoup。前端没有引框架，就是原生 HTML/CSS/JavaScript，图表用 ECharts。这个组合的好处是所有依赖都能用 pip 装上，环境迁移不会有坑。

## 四、系统总体结构与目录说明

项目根目录是 `rumor_detection_project`，按"一个脚本管一件事"的思路拆文件：

```
app.py          Flask 主程序，页面路由和所有 /api/ 接口
config.py       公共配置：数据库连接、端口、模型路径、停用词
database.py     ORM 三张表的定义 + 所有增删改查函数
init_db.py      建库建表脚本，支持 --drop 重建和 --check 检查
spider.py       爬虫，真实抓取失败时自动读本地 CSV
preprocess.py   文本清洗、去重、jieba 分词、TF-IDF
train_model.py  训练 TF-IDF + 逻辑回归，模型存到 models/
train_lstm.py   训练 LSTM，扩展部分
predict.py      加载模型做预测，被 app.py 和命令行共用
data/           示例数据 CSV
models/         训练好的模型文件
static/         前端样式和脚本
templates/      前端页面模板
docs/           各类文档
```

有几处拆分是返工改出来的。最早业务流程写在 app.py 里，后来预测要在命令行单独调试，就抽成了 predict.py；再后来发现命令行和接口都在重复"读文本—算概率—写库"，干脆把写库也收进 database.py。现在 app.py 里基本看不到 SQL，每个接口就是调几个函数再拼返回值。

## 五、数据库设计

三张表，字段都不多。

**raw_messages（原始消息表）**。存爬进来或者从 CSV 读进来的消息。主要字段有 `text`（正文）、`image_url`、`source`（来源平台）、`timestamp`、`rumor_prob`（模型算的概率，没检测时是 NULL）、`status`（未处理 / 已检测 / 已处理）、`nature`（人工定的性质）、`processed_time`、`keywords`（这条消息命中的词，逗号分隔）。`timestamp` 和 `status` 上建了索引，列表查询经常按这两个排序和过滤。

**processed_messages（已处理文本表）**。人工校验完成后从 raw_messages 复制一条过来单独存。冗余存一份正文有点浪费，但查已处理记录时不用关联原表。这张表的 `raw_id` 加了唯一约束，一条原始消息只对应一条处理结果，反复点校验不会插出两条。

**keywords（关键词表）**。就 `word` 和 `frequency` 两个业务字段，词云的数据源。word 上有唯一约束，重复统计时更新次数而不是插新行。

状态值没做成数据库枚举，而是在 database.py 里定义成 `STATUS_PENDING`、`STATUS_DETECTED`、`STATUS_VERIFIED`、`NATURE_RUMOR`、`NATURE_NORMAL` 几个常量，其他地方都引用常量，避免手写中文写错字。

## 六、数据采集与预处理

爬虫按"先真实抓、抓不到就兜底"的思路写。`spider.py` 里接了今日头条、百度、腾讯、新浪、澎湃、中新网六个公开的新闻热榜和滚动页，都是不用登录就能打开的地址，请求头、翻页、解析都写了，其中今日头条、腾讯、新浪给的是 JSON 接口，另外三个是 HTML 页面。真实网站的反爬策略经常变，课程演示又多在校园网环境下进行，谁也不敢保证答辩那天能抓到，所以脚本里做了判断：六个源是各自独立的，一个失败不影响其他几个，合起来一条都没抓到，就自动切到读 `data/sample_data.csv`。CSV 里放了 50 条我们自己编的模拟消息，25 条偏谣言、25 条正常内容，时间、来源、配图地址都填了值，格式是 UTF-8 带 BOM，Excel 直接打开不会乱码。启动参数是 `--source auto|web|csv`，默认 auto，演示前也可以手动指定 csv 跳过网络。

入库存到 raw_messages 之前会和库里已有的正文比一次，重复的直接跳过。量不大，就把已有正文全捞出来放集合里比对，比一条条查库快。

预处理在 `preprocess.py` 里，做了四件事：

1. **清洗**。去掉 URL、@用户名、话题符号、HTML 标签、表情符号和多余空白，全角标点统一成半角。
2. **去重**。正文完全相同或者清洗后相同的只留一条。
3. **分词**。jieba 分词，同时过一遍停用词表。停用词写在 config.py 里，除了“的、了、是”这些常规的，还去掉了“转发”“微博”“分享”这类到处都是但不带信息的词。爬虫抓的是新闻稿，稿子里“查看”“表示”“报道”“记者”“日讯”这种套话也很高频，一开始没管，结果词云第一屏全是这些词，看着不像关键词，后来一起加进停用词表了。
4. **向量化**。用 TfidfVectorizer 把分词结果转成 TF-IDF 矩阵，限制了 `max_features=5000`，`ngram_range` 取 (1,2)，单个词和相邻两个词都当特征，这样"不明""来源""不明来源"会分别进模型。

## 七、谣言检测模型

主模型是 TF-IDF + 逻辑回归，`train_model.py` 负责训练。训练样本有三个来源：`data/sample_data.csv` 里 50 条人工标注数据、数据库里已经人工校验过的记录，以及爬虫抓来的新闻正文。第三条是按“热榜和滚动页的新闻是媒体发布的真实信息”这个假设，把来源属于 `config.NEWS_SOURCES` 的消息统一当成非谣言，训练时可以用 `--no-news` 关掉。流程是把预处理后的文本转向量，按 7:3 划分训练集和测试集，训练完做 5 折交叉验证，再把向量器和模型分别用 joblib 存成 `tfidf_vectorizer.pkl` 和 `lr_model.pkl`。

为什么要加爬虫新闻这一类样本：TF-IDF 的词表只由训练样本构成。如果只喂那几十条模拟数据，真实新闻里的词模型一个都没见过，一条新闻转向量后全是 0，逻辑回归算出来就是截距那个常数，界面上表现为一大批消息的概率都挤在同一个值上（我们调的时候见过连续二十多条都是 49.6%）。把新闻正文纳入训练以后词表覆盖了新闻用词，概率才有高低区分。

跑出来的指标是：5 折交叉验证平均 F1 约 0.54（各折波动比较大），测试集准确率约 0.96，谣言这一类召回率约 0.5、精确率 1.0。指标得实话实说：样本只有三百来条，其中非谣言占了绝大多数（爬来的新闻都是非谣言），类别很不均衡，所以“准确率高”主要来自把新闻都判对，“谣言召回率 0.5”说明一半的真谣言还是漏掉了。另外训练样本和演示数据有重叠，这个数字不能当成真实的泛化能力，想验证得另找没参与训练的数据，这部分我们没条件做。

选逻辑回归不是因为它准，而是因为它可解释。深度模型只能给一个概率，老师问"为什么"不好回答。逻辑回归的打分是各个特征值乘系数再求和，把某条消息的词和对应系数按位相乘，正贡献最大的几个词就是判成谣言的主要依据。`predict.py` 里的 `explain_keywords` 就是干这个的，界面上"命中关键词"那一列的数据从这里来。

判定阈值默认 0.5，写在 config.py 里。详情页和接口都支持临时传别的阈值，方便演示"阈值调高以后召回率怎么变"。

LSTM 那一版写在 `train_lstm.py` 里，思路是 jieba 分词后建词表、做词嵌入、过 LSTM 再取 sigmoid 输出。这部分我们没装 PyTorch，没有实际跑通验证过，属于后续可扩展的部分，不算在已完成的功能里。

## 八、后端接口设计

后端所有接口返回统一结构：`{"code": 0, "msg": "提示文字", "data": {...}}`，code 为 0 表示成功，非 0 表示出错，原因写在 msg 里。前端拿到的成功和失败可以用同一套逻辑处理。

页面路由两个：`/` 是首页，`/detail/<id>` 是详情页。接口九个：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/overview` | 统计数字 |
| GET | `/api/messages` | 消息列表，支持分页、关键词、概率区间、性质、只看未处理 |
| GET | `/api/message/<id>` | 单条消息详情 |
| POST | `/api/detect/<id>` | 跑模型检测，写回概率和关键词 |
| POST | `/api/detect-all` | 一键检测，把所有没人工校验的消息重跑一遍 |
| POST | `/api/verify/<id>` | 人工校验，参数 nature |
| GET | `/api/processed` | 已处理文本列表 |
| GET | `/api/keywords` | 词云数据 |
| GET | `/api/search` | 关键词 + 概率区间搜索 |

有几个地方做了防护。`page_size` 上限锁在 100，防止有人手改 URL 传个很大的值把库拖垮；阈值参数如果不是 0~1 之间的数，按默认值处理；对已人工校验过的消息调检测接口会被拒绝；消息不存在返回 404 而不是 200。`/api/detect-all` 只处理状态不是“已处理”的消息，人工校验过的结论不会被覆盖，返回里带上成功条数和耗时。

数据库连接这块，`database.py` 用的是 `scoped_session`，同一个线程拿到同一个 Session。Flask 每个请求一个线程，所以在 `app.py` 里注册了 `@app.teardown_appcontext`，每个请求结束调用 `close_session()` 释放 Session。不写这一段连接会一直被占着，跑久一点 MySQL 就报连接数超限。

## 九、前端界面实现

前端没用框架，两个模板加一个 CSS 一个 JS。页面本身是服务端渲染的空壳，数据全靠 JS 调 `/api/` 拿，所以详情页一张模板就能复用，从列表点哪个 ID 进来都行。

JS 里给 fetch 包了 `apiGet` 和 `apiPost`，统一处理 `code != 0`，出错直接抛异常，调用处一个 try/catch 就够。正文里可能有尖括号，渲染前统一走 `escapeHtml` 转义，不然带 `<script>` 的正文会把页面结构搞乱。

页面靠 `<body data-page="index">` 和 `data-page="detail"` 区分，同一个 script.js 里根据这个值决定初始化哪套逻辑。列表里的"检测"按钮是动态生成的，事件监听用事件委托绑在 tbody 上，直接绑按钮换个页就丢了。

词云用 ECharts 的 wordCloud 扩展，从 CDN 引。考虑到演示环境可能没网，JS 里做了判断：`echarts` 没加载出来就换成按字号大小表示词频的文字云兜底，效果朴素些，但不会空着一块。

## 十、六人分工、进度与不足

分工按模块走，每个人负责一条线，接口对接前先把字段名对好。

| 组员 | 负责内容 | 产出文件 |
| --- | --- | --- |
| 甲 | 项目统筹、数据库设计与实现 | config.py、database.py、init_db.py、requirements.txt |
| 乙 | 爬虫与数据集 | spider.py、data/sample_data.csv |
| 丙 | 文本预处理与模型训练 | preprocess.py、train_model.py、train_lstm.py |
| 丁 | 后端接口 | app.py、predict.py |
| 戊 | 前端界面 | templates/index.html、templates/detail.html、static/style.css、static/script.js |
| 己 | 测试、文档与答辩材料 | 接口测试、docs/ 下各文档、PPT 与演示视频 |

进度上分四段走：环境搭建与建库建表、数据采集与预处理、模型训练、界面与联调。联调花的时间最多，主要卡在两处：数据库密码和编码，以及前端拿不到数据时不好判断是接口问题还是渲染问题。后来在启动时加了自检，把数据库通不通、模型文件在不在直接打出来，排查快了很多。

不足的地方我们也清楚：

- 模型训练数据和演示数据同源，指标虚高，实际的泛化能力没有验证；
- 把爬来的新闻统一当成非谣言参与训练，这是个假设不是人工标注：如果某条热榜新闻本身就是不实信息，它会被当成“非谣言”教给模型，这是这类做法的固有风险；
- 非谣言样本比谣言多得多，模型偏向判“非谣言”，谣言召回率只有 0.5 左右；
- LSTM 只写了代码没跑通，因为没装 PyTorch；
- 爬虫的真实抓取部分依赖目标网站的页面结构，对方改版就会失效，只能靠 CSV 兜底；
- 系统没有登录和权限控制，任何人都能点校验按钮，做真实系统的话至少得区分标注员和管理员；
- 词云只做了全量的词频统计，没有按时间或按来源分开看，分析粒度比较粗。

这些列出来的都是后面可以继续做的方向，不是已经做完的功能。
