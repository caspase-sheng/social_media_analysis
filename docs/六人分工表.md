项目：社交媒体谣言检测系统（谣言检测界面设计）
课程：软件工程综合实践
小组人数：6 人

## 二、各人分工说明

### 甲　组长 / 数据库

负责的是一条主线：环境、数据库、以及整体节奏。

具体做的事：跟我们讨论定下做谣言检测这个题目；把项目拆成"环境—数据—模型—界面—联调"五段并排期；在 `D:\conda` 下建了 `rumor_detection` 环境并整理 `requirements.txt`；设计 `raw_messages`、`processed_messages`、`keywords` 三张表；把常用的增删改查封装成函数写进 `database.py`，并在 `init_db.py` 里做了建库建表和 `--drop` 重建。

数据库这块有两次返工：一次是发现列表查询会按时间和状态排序过滤，补了索引；另一次是 `processed_messages` 一开始没加唯一约束，测试时同一条消息被点了两次校验插出两条记录，后来给 `raw_id` 加上了 unique。

### 乙　数据采集

负责数据的来源。

具体做的事：写了 `spider.py` 的抓取部分，接了今日头条、百度、腾讯、新浪、澎湃、中新网六个新闻源，每个源一个函数，请求头、翻页和解析都在里面；六个源互不影响，某个源出错只丢它自己的数据，合起来一条都没抓到才切到读本地 CSV；另外处理了几个源接口字段不一致的问题，比如图片字段有的给字符串有的给字典，还有中新网页面声明的编码和实际内容对不上，写了自动识别编码的逻辑；手工整理了 `data/sample_data.csv`，50 条消息，25 条偏谣言 25 条正常内容，时间、来源、配图地址都填了值，文件用 UTF-8 带 BOM 保存，方便 Excel 直接打开。

入库去重那段也是乙写的：把库里已有的正文全捞出来放集合里比一次，重复的跳过。选这个笨办法是因为数据量不大，比一条条查库快。

### 丙　算法

负责从文本到概率这一整段。

具体做的事：在 `preprocess.py` 里写了清洗（去 URL、@用户名、话题符号、HTML 标签、表情、统一标点）、去重、分词和向量化；在 `config.py` 里整理了停用词表，除了常规虚词，还去掉了"转发""微博""分享"这类在社交平台上到处都是但不带信息的词；在 `train_model.py` 里训练 TF-IDF 加逻辑回归，跑 5 折交叉验证，结果用 joblib 存到 `models/`。

踩过的坑记录在调研报告里：中文直接丢给 `TfidfVectorizer` 会得到全零矩阵，因为它默认的 `token_pattern` 只认两个及以上字母数字，中文必须先分好词再拼回去。

`train_lstm.py` 也写了，但因为环境里没装 PyTorch，没有实际跑通，属于后续可扩展的部分。

### 丁　后端开发

负责接口和联调，也是这份文档和调研报告的执笔人。

具体做的事：定了接口的统一返回结构 `{code, msg, data}`；写了 9 个 API 和 2 个页面路由；把"读文本—算概率—写库"抽成一个可复用的流程，命令行和服务接口都走同一套；在 `predict.py` 里做了模型缓存，避免每次请求都读磁盘；在 `app.py` 里注册 `@app.teardown_appcontext` 释放 Session，并加了启动自检。

联调阶段的问题基本都是丁在查：conda 没进 PATH、`run.bat` 的 GBK 编码把中文提示读坏、jieba 装成只剩 dist-info 的空壳、MySQL 回收空闲连接导致报错、Session 没释放导致连接数超限。这几件事在 `系统调研总结报告.md` 里有详细记录。

### 戊　前端开发

负责界面的全部实现。

具体做的事：写 `templates/index.html` 和 `templates/detail.html` 两个模板；`static/style.css` 从零写，没引 UI 框架；`static/script.js` 里封装了 `apiGet` / `apiPost`，按 `<body data-page>` 的值区分首页和详情页两套逻辑；实现了分页、搜索筛选、标签页切换、概率进度条、状态标签、词云；列表里的检测按钮用事件委托绑定，正文渲染前统一走 `escapeHtml` 转义。后来补的几项：列表按时间 / 概率排序的切换、点词云上的词直接筛选消息、一键批量检测按钮，以及单条检测完重新拉列表让概率列实时刷新。

词云用的是 ECharts 的 wordCloud 扩展，从 CDN 引，同时写了没网时用字号表示词频的兜底方案。样板文字提示词原本写的"疫苗"，自测时发现数据里没这个词，改成了"小区"。

### 己　测试与文档

负责验收和材料。

具体做的事：用 Flask 测试客户端把 9 个接口逐一跑过，包括参数非法、id 不存在、对已处理消息重复检测这几个异常分支；在浏览器里逐项验证界面，覆盖统计数字、分页、搜索、重置、标签页切换、词云渲染、点词筛选、排序切换、一键检测、检测提示条；整理各类文档；做 PPT 和演示视频。

测试中提出过一个有效的改进意见：前端页面空白时看不出问题出在哪一环，建议后端加启动自检并统一错误返回。这条后来由丁实现。

## 三、协作方式

**接口先行**。开工前先把接口的路径、参数名、返回字段定下来写成表格，前端按这个写请求，后端按这个写返回，避免各写各的。

**统一的目录约定**。配置全放 `config.py`，数据库操作全放 `database.py`，业务代码不直接写 SQL。这样几个人改不同文件不会撞车。

**主分支由甲合并**。各人负责的文件单独改，改完先自测再交给甲合并，合并前跑一次 `python app.py` 确认能起来。

**问题集中记录**。联调期间遇到的问题统一记在一份共享笔记里，写清楚现象、原因、解决办法，后来整理成了 `docs/常见报错与解决.md`，也成了调研报告第六节的素材。
